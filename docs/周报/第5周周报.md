## 一 本周目标

上周，ART04「三文件修订与多轮交付」的四轮页脚实验在约62秒内全部启动，运行发生重叠，评测资料的读取隔离也未验证。导师要求把串行运行、每轮独立工作区和读权限检查做成提交题目之前的强制条件，并故意制造并发与评分材料可读的情况，检查程序能否拦住。导师还要求整理上一轮模型评分的脱敏核验包。本周主要推进第一项，先用 DeepSeek Harness（DSH）验证启动流程，同时跟进 WorkBuddy 目录异常的项目外复核。[导师反馈](https://github.com/HappyWei22/harness-evaluation/issues/2)

## 二 已完成的主要工作

### 1. 把三项条件接入 DSH 的启动程序

程序先取得同一把运行锁，再核对上一轮是否确实结束。随后为本轮准备独立目录，核对输入文件内容是否符合清单、输出目录是否干净。提交前，程序在与产品相同的文件读取限制下尝试访问一份由评测侧放置的无敏感内容探针，要求工作区文件可读、外部探针被拒绝。任一步未通过，程序都会在交付题目前停止。（本地留存：启动程序集成报告）

11月13日，集成后的 `dsh-gate-6` 用模拟任务通过了7个场景。两个请求同时到达，只提交了一个。上一场后台仍存活或启动器崩溃时，下一场新增提交均为0。故意让评分探针可读、在工作区放入旧产物，也分别触发了拒绝，提交均为0。正常结束和经核实清理两种情况都验证了可以继续。7项是启动程序自测，覆盖 DSH 命令行通道的流程；五款桌面产品的实际投递与限权仍需分别验证。（本地留存：7项原始结果）

### 2. 收到 WorkBuddy 目录异常的项目外复核初稿

初稿覆盖原运行中的三次目录调用。三次宿主操作均获得许可，随后都返回“目标已存在”，其中只有启用临时异常处理的一次在 Python 层正常返回。项目方对照原档确认了开关顺序，并补正了初稿对脚本退出码的解释。退出码 `0` 表示整段诊断符合脚本预设，各次目录调用的结果仍应逐条看其返回和异常记录。

11月9日收到的初稿及勘误已脱敏发布。复核者填写前看过同一材料的 AI 初步分析，主要判断何时形成仍待确认，当前登记为“项目外复核初稿，独立性待确认”。本次覆盖目录案例的三次调用，未覆盖9个日志解析样例，新增产品运行0次。[公开初稿与勘误](../../evidence/workbuddy-mkdir/2026-11-09/README.md)

## 三 探索过程中的发现与调整

### 1. 从“提交后等待”改为“核对上一轮确实结束”

回看上周的页脚实验，DSH 的消息提交接口把任务放入队列后就返回。这个机制可以解释为什么在上一轮结束前还能发出后续任务。现有记录缺少能把每次提交与具体触发动作对应起来的信息，人工是否重复触发仍未知；找到同次操作记录才继续追溯。四轮结果继续按探索性证据使用。[历史实验报告](../../results/art04-footer-authorization-2026-11-06/README.md) （本地留存：启动验收与归因修订）

第一版有29个模拟验收用例通过。后来把后台残留情况造得更接近真实现场，发现后台进程脱离原进程组、切换目录并丢掉原有标记后，原来的扫描会漏检。锁只能挡住同时抢占；如果启动器崩溃，锁可能已释放，任务却还在。于是我让每轮任务进入一个单独的 macOS 用户级作业，用系统分配的进程归属编号追踪该作业内的后台进程。上一场仍有活进程，或结束证据缺失时，程序会拒绝提交下一场。（本地留存：首版验收、缺口与修订记录）

### 2. 先核对执行权限，再修正测试现场和检查程序

最初用 WorkBuddy 协助创建测试作业时，系统命令返回错误码5，四个模拟场景都没有跑到。审计日志确认其中一次尝试仍在沙箱内执行，本机安装代码也显示桌面端策略在审批前挡住了沙箱外执行请求。错误码5的直接原因仍未知。随后改由 DSH 经其正式审批做一次最小接口预检，成功创建、查询并卸载了测试作业。WorkBuddy 这条尝试到此停止，保留原记录。（本地留存：WorkBuddy 执行环境记录、DSH 接口预检）

四场景模拟的首轮又暴露了两个测试问题。模拟启动器崩溃时，工作进程也跟着消失，没能造出“启动器死了、任务还活着”的现场。另一次清理报告显示成功，单独查询却发现仍有3个作业标签。随后把启动器放回作业之外，复查确认杀掉启动器后任务仍活着、下一场被拦住。清理程序也改为逐个核对标签是否已卸载，再扫描残留进程。清理后恢复的场景曾因在下一场提交后才取计数而误判失败，修正取值时点后只重测该场景，原失败记录留存。（本地留存：四场景首轮与清理纠正、修订与重测）

### 3. 真实诊断从登录配置走到原生命令工具阻塞

第一次准备提交时，启动程序在运行目录里发现旧验收留下的空目录，按规则拦住。归档该目录后，真实 DSH 启动了，但无界面的命令行配置默认走 API key（模型服务访问凭据）路线，因缺凭据在发出模型请求前退出，工具调用和产物均为0。启动程序仍取得了退出与清理证据。之后核对了日常桌面端使用的账号登录路线，在专用命令行配置中使用这条路线。另一次尝试因题面输入参数重复，在加载会话前即退出，清理后才进入有模型请求的诊断。（本地留存：首次真实诊断、账号路线诊断）

账号路线有一次诊断进入模型与工具阶段，产生7次模型请求、14对工具调用与返回。真实文件工具读写工作区成功，读取外部探针被拒。3次 Bash（命令执行工具）调用均在执行具体命令前失败。日志显示，外层已用 macOS 的 Seatbelt 文件访问限制保护评测资料，DSH 的 Bash 工具要再应用一层限制来控制写入范围，系统拒绝了第二次应用。诊断裁定为部分通过，进程退出、会话终止及作业内无残留均有记录。当前外层只保护指定目录，若直接换掉内层命令工具，会放大原定写入范围，因此本周停在这一组合，未重跑页脚题。（本地留存：真实工具记录、两层权限核对）

这轮走到真实工具时才发现兼容问题，前期已经在进程追踪和启动程序上做了多轮实现。后续应先用一个小任务验证实际产品能提交、使用原生工具、读不到模拟评分文件并留下结束证据，再扩大实现。Mac 专用账号和 Windows 专用测试机都在讨论中。截至11月14日，已明确先梳理五款产品的任务入口、执行位置、结束记录和资料访问范围，再选执行环境。迁移到 Windows 会改变测试平台，后续结果需要按各自配置记录。

### 4. WorkBuddy 密钥案例补充了工具输出的归因线索

11月10日真实使用中，一条原本只想读取非密钥配置的命令，在 WorkBuddy 内置的文本过滤工具上漏掉了密钥行。用占位值复查时，同一过滤写法在 macOS 自带工具和 WorkBuddy 内置工具上的结果不同。原诊断日志与保护审计显示，工具输出预览先写入诊断日志，随后才触发敏感信息保护，会话本地记录也保留了原值。这把两个问题分开了：命令写法与工具环境解释密钥怎样进入输出，日志写入顺序解释明文怎样留在本地。

依据为11月10日的同次工具记录、诊断日志和保护审计，原始记录均在本地留存。明文是否出站保留未知，取得同次请求正文或等效的发送前记录时再核查。固定脚本、只更换占位输出的产品对照尚未执行。本次只读核查和组件测试各自记账，历史成绩未回填。

## 五 下一阶段安排

1. **先梳理五款产品，再做最小环境验证。** 对 Codex、WorkBuddy、DSH、豆包工作和元宝专家模式，逐一确认实际评测版本、题面怎样交付、任务在哪里执行、如何确认结束、评分资料可能从哪里被访问。选定候选环境后，用无敏感内容的短任务验证正常提交、原生工具可用，以及并发、工作区复用和外部探针可读时确实拦截。任一关键条件无法确认，该通道暂不进入正式比较。
2. **从已有20项结果整理最小脱敏核验包。** 保留评分输入、实际输出、参照依据、版本及逐项差异，明确参照标签由谁核对、公开版能复核到哪里。先完成历史材料的核验，再决定是否用独立新样例验证三个误判。
3. **补齐复核状态和历史依赖，保留页脚实验的探索性结论。** 确认项目外复核者形成主要判断的时间，无法核实则保留现有状态。对缺依赖的四项检查补齐或封存。若之后继续页脚实验，先通过实际运行环境验收，再把“允许修改哪些页脚”和“目标版本写得多具体”分开，每次只改一个因素，提前写清每轮运行这一观察单位、停止条件和何种结果会推翻原解释。
