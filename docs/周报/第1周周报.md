# Harness能力评测与失败分析

第1周周报

尚星纬

项目材料：[Harness能力评测与失败分析](https://github.com/HappyWei22/harness-evaluation)。

## 一 本阶段目标

这一阶段，我想先弄清楚怎样评测Harness，尤其是任务失败后，能否从执行记录中找到具体的问题。例如，程序已经报错，产品却没有据此继续处理，这时需要检查它是否收到了完整的报错信息，再考虑问题出在工具结果回传，还是后续处理上。只看最终任务有没有完成，还不足以作出判断。

目前选取Codex、WorkBuddy、DeepSeek Harness（DSH）、元宝专家模式和豆包办公作为测试对象。本阶段先通过论文学习和试跑熟悉各产品，逐步把已有评测维度整理成具体题目，明确每道题要检查什么、怎样评分，以及需要保存哪些记录。

## 二 已完成的主要工作

我阅读了《The Scaffold Effect》和《Harness-Bench》，学习控制比较条件、检查实际文件和分析执行过程的方法；随后筛选公开办公题，检查输入与评分程序，并开展跨产品试跑。

目前已确定七个评测维度，并开展三道信息回传测试和一道上下文管理基础测试，保存输入、提示词、判分规则和已有现场。另有本地评测工作台，辅助准备材料、登记状态和归档，产品任务仍由我在原生界面提交。

取证工具方面，在社区插件dsh-context 0.72.0上增加了“导出所选上下文JSON”和“下载原始会话日志ZIP”两个按钮。前者把插件依据日志还原的某一步上下文保存成结构化文本，后者调用DSH已有日志下载功能。这便于保存现场和事后核对。已在DSH 0.2.0-rc.2中使用已有会话点击验证；它没有截获实际发给模型服务的请求，也没有证明长会话压缩等场景均可靠。源码和贡献范围见[导出扩展说明](https://github.com/HappyWei22/harness-evaluation/blob/887441f22008afa25794e49f08fce48659404b63/tools/dsh-context-export/README.md)。

## 三 探索过程与方法调整

**最初为什么选择公开任务？** 我最初希望通过较多真实任务覆盖不同操作，再从失败中寻找Harness问题。选择公开题的考虑是，它们有具体业务背景和既有评分程序，可以减少自行出题时凭感觉判断的情况；让五款产品处理相同材料，也便于比较交付结果。因此，前期花了较多时间查找题目、检查附件、核对评分要求和准备运行环境。

**实际推进时遇到了什么困难。** 一方面，不少工作停留在测试前的准备。比如，表格公式是否需要重新计算、评分程序是否要求固定坐标、题面是否已经说明相关要求，都需要确认。否则，一个零分可能来自验收条件不清楚，未必是产品没有完成业务要求。另一方面，任务真正运行后，复杂结果也不容易解释。财务模型补全同时涉及业务理解、公式计算、文件格式和工具执行；最终数值不对，可能发生在多个环节。仅凭失败分数，很难决定接下来先查哪一步。

这让我发现，前期虽然已经有评测方向和能力维度，却没有尽早把它们落实成可观察的操作。我把“增加测试数量”和“找清Harness问题”之间的关系想得过于直接。公开题能够暴露异常，但如果没有事先确定要检查什么，增加题量也可能只是积累更多难以解释的结果。试跑帮助我熟悉了产品入口、文件检查和日志获取，不过工作重心应该更早回到评测标准上。

**后来具体怎样调整？** 我开始先把标准写成问题：要观察什么行为，怎样让这种行为发生，应该保留哪些材料，满足什么条件才得分。以长输出为例，先用固定程序生成模拟报告，观察工具是否只返回一部分内容，也就是截断；再分别检查有没有截断说明、有没有全文入口、能否从入口读到缺少的信息，以及保存文件是否完整。第二阶段由我明确要求读取，因此它检查的是入口和后续获取能力，没有评价产品能否自主处理截断。这样，一次测试可以对应几个明确问题，不必依赖模型先完成复杂业务计算。

**评分过程还暴露了测试自身的问题。** 基础回传题安排程序分别正常结束和故意报错，原本用于比较两种状态与对应字段。但WorkBuddy本轮错误模式在保存评测回执时就提前退出。回执是测试程序给评测方保存的预期结果；保存失败后，目标错误字段尚未生成。此时看不到字段，不能说是Harness把字段丢了，应记为未有效测试。这个例子提醒我，判分前必须先检查实际操作和测试条件，不能为了得到失败案例跳过这一步。

对于缺少记录的项目，也需要保留未知。信息回传要看工具实际返回；检查对话中是否采用最新要求，则可以使用连续可见问答。证据是否足够取决于具体观察对象，不能一律以有没有后台日志判断产品好坏。目前，专项测试让现象更具体，但不同模型、产品自带指南和环境仍会影响结果。后续仍需要真实任务检查这些专项行为是否影响交付，而不能把一次专项差异直接当作内部根因。

## 四 专项测试方法与初步观察

本阶段先检查两个问题：工具执行后，信息是否准确返回；用户修改要求后，产品是否采用最新版本。对应任务如下，完整输入与规则见[用例和方案](https://github.com/HappyWei22/harness-evaluation/blob/887441f22008afa25794e49f08fce48659404b63/docs/%E8%AF%84%E6%B5%8B%E6%96%B9%E6%A1%88.md)。

| 测试任务 | 怎样操作 | 检查什么 |
|---|---|---|
| 基础回传（FB01） | 运行同一程序的正常模式和预设错误模式 | 退出状态与关键字段是否准确返回 |
| 较长结果回传（FB02） | 一次输出200行模拟报告 | 报告不同位置的四个指定字段是否保留 |
| 截断后完整结果获取（FB03） | 一次生成256 KiB，即262144字节报告；确认截断后，再要求按首次入口读取 | 截断提示、入口、实际读取和全文保存 |
| 多轮要求更新（CTX01） | 同一会话先登记活动，再局部修改，最后要求输出当前记录 | 保留未改条件，并采用更新后的条件 |

在完整结果获取题中，DSH本轮提供入口、取回指定内容，保存文件与预期逐字节一致；WorkBuddy取回指定信息，但保存文件多2058个回车字符，移除后正文一致，按严格字节保存规则扣分。Codex本轮指定调用提示截断，首次没有提供可用全文入口，底层是否另存全文仍未知。豆包补充检查支持读取和全文准确两项，首次提示及入口仍缺证据；元宝缺必要工具正文，暂时无法判断。这些现场支持本轮具体行为差异，没有形成完整20分排名。依据见[信息回传逐项记录](https://github.com/HappyWei22/harness-evaluation/blob/887441f22008afa25794e49f08fce48659404b63/results/information-feedback.md)。

多轮要求更新题使用一个简单的校园活动登记：先给出编号ACT-27、地点A教学楼、预算3000和币种CNY；第二轮只把地点改为图书馆、预算改为4500；第三轮要求输出当前记录，不再补答案。五款本轮都保留了编号和币种，并采用新地点、新预算，各为4/4。但题目只有三轮，多款在第二轮已汇总全部有效值，因此还不能说明长对话或压缩后的信息保持能力。实际问答见[上下文测试记录](https://github.com/HappyWei22/harness-evaluation/blob/887441f22008afa25794e49f08fce48659404b63/results/context-update.md)。

## 五 当前不足与下一阶段安排

现有信息回传记录仍有未知、待查和未有效测试。豆包历史确认9分中，只有4分有充分归档支持，另5分待补现场。五款模型与环境未完全统一，样本也少，不能把全部差异归为Harness的独立影响或长期表现。

下一阶段优先把其余维度的题目确定下来，再完成各维度测试：

1. 明确失败恢复、权限边界、产物保存与交付、停止条件、可观测性的具体用例，同时补齐上下文管理的复杂题。每题写清目的、输入、操作、完成条件、判分和所需证据。
2. 按确定的用例组织五款产品运行，记录实际配置、人工操作、工具返回和交付物，确认测试条件成立后再评分。
3. 汇总各维度结果，区分通过、未通过和证据不足，形成覆盖范围清楚的阶段报告。已有记录中能够补齐的关键证据在这一过程中同步补充。

完成这轮维度测试后，再从证据较完整的失败中选择案例开展原因验证。具体安排见[下一阶段工作](https://github.com/HappyWei22/harness-evaluation/blob/887441f22008afa25794e49f08fce48659404b63/docs/%E5%BE%85%E5%AE%8C%E6%88%90%E4%BA%8B%E9%A1%B9.md)。
