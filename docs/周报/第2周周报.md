# Harness能力评测与失败分析

第2周周报

尚星纬

2026年10月18日—10月23日

## 一 本阶段目标

上周，我将工作重心从寻找公开任务、比较最终成败，调整为围绕评测维度设计具体用例。本周主要把这一方法用于上下文管理、失败恢复、权限边界、产物保存与交付、停止条件五个方面，组织五款产品运行，并核对操作记录与实际文件。

本阶段想回答的问题是：产品是否保留了更新后的要求，出错后是否从正确位置继续，工具操作是否遵守实际权限，文件是否完整交到用户手中，以及结束时是否准确说明完成范围。这些问题不能只看最后一句“已完成”，还需要对应的工具返回、文件和状态证据。

测试对象仍为 Codex、WorkBuddy、DeepSeek Harness（DSH）、元宝专家模式和豆包工作。各款沿用其原生模型与工具配置，因此本轮结果反映的是产品整体在指定条件下的表现，尚不能把差异独立归因到某个 Harness 组件。

## 二 已完成的主要工作

本周围绕上述五个方面准备或执行了专项用例，并将输入、提示词、判分规则、运行记录、实际文件和评分依据对应保存。当前进展如下。

| 评测方向 | 本周实际推进 | 当前结论范围 |
|---|---|---|
| 上下文管理 | 完成五款多轮状态保持观察，核对压缩事件及最终输出 | 五款最终内容均符合16项检查，但只有三款确认发生手动压缩，复杂部分正式分仍留空 |
| 失败恢复 | 完成参数报错后继续导出、批量导出中断后续做两类测试 | 四款确认15项；元宝确认7项、8项过程证据不足 |
| 权限边界 | 执行写入范围、单次授权后续调用、链接与子进程访问等测试 | 保存了条件性通过、明确反例和未知；持续许可撤销部分未测 |
| 产物保存与交付 | 完成技能包、档案移交、三文件修订和定稿包续修四类任务 | 已核对五款20份计分记录，保留实际失败与8分待定 |
| 停止条件 | 完成档案暂存、异常批处理、正常恢复和受阻恢复四个场景 | 四款各确认10项；元宝确认3项、7项未知，本轮已归档 |

这些“确认项”来自各维度预先规定的观察条件，不能与文件检查程序输出的检查数量混用，也没有将它们直接相加形成100分产品排名。

取证方面，本周进一步区分了三类材料：产品的完成声明、原生操作及返回、实际文件与状态。对能够访问本地现场的产品，保存工作区和原生日志，并核对复制前后的文件指纹；对只能取得窗口和部分下载件的产品，则明确记录证据覆盖范围。文件指纹可以确认副本是否改变，不能单独证明产品执行过哪些动作。

## 三 探索过程与方法调整

**首先，最终答对不代表测试条件已经成立。**

上下文管理原本希望检查信息经过压缩后是否仍被保留，也就是产品将较长历史整理成摘要后，能否继续采用最新要求。五款最终输出都符合16项内容检查，但继续核对发现，各款实际经历的过程并不相同。

DSH、WorkBuddy和Codex有手动压缩记录；豆包、元宝尚未取得足以确认压缩的证据。进一步检查还发现，WorkBuddy和Codex的压缩后记录仍保留了五轮用户业务原文，不能据此说它们只靠精简摘要完成了任务。因此，我将“内容正确”“压缩发生”和“正确结果是否依赖压缩摘要”分开记录，没有把五款全部写成压缩能力满分。

**其次，权限测试必须先确定产品真正限制了什么。**

最初准备权限用例时，我将任务目录和模拟外部文件分别放进不同文件夹。但目录名叫“outside”，并不意味着产品原生系统禁止访问它。元宝拟定的几个目录都位于其报告的可写根目录之内，现有证据无法建立受限目标，因此复杂题停在预检，没有继续执行探针，也没有把它记成越权失败。

WorkBuddy则提供了另一种情况：基础题在所记录的默认条件下实际写入了外部模拟文件；后续人工增加精确文件规则后，才观察到指定访问被禁止。这说明两个实验条件下的行为不同，后者不能覆盖前者，也不能据此声称默认边界问题已经修复。

这些经历让我认识到，权限评分前必须先说明允许范围、原生规则和批准方式，否则一次写入成功或失败都可能被错误解释。

**再次，文件存在、文件正确和用户能够取得文件，需要分别检查。**

产物交付测试中，有些文件在目录里存在，但用户无法从原回复入口取得；也有多文件修订遗漏页脚版本、续修日志行结构错误，以及实际下载件与预期字节不同的情况。因此，我将内容、文件集合、版本、交付入口和实际取件分别核对，避免看到“已生成”就认定交付完成。

检查程序本身也出现了问题。例如，旧检查规则曾因固定整句匹配而误判Codex的页脚版本。复核时，我保留原检查结果，再单独核对批准版本，并用相同方法回查其他产品。这提醒我：程序检查可以提高核对效率，但检查失败不一定就是产品失败，仍需确认它是否准确表达了题目要求。

**最后，证据不足需要有明确的收尾方式。**

本周多次遇到产品声明验证通过，但现有材料没有完整返回或最终状态的情况。我没有继续用口头说明补分，而是记录缺少什么、已经检查到哪里、哪些判断可以确认。

停止条件测试收尾时，也将原先分散在聊天中的判定写入逐项记录，核对分数与证据引用，并保留此前被修正的判断。这样，后续查看者可以知道一项分数为什么通过或留空，不必依赖聊天中的最后一句结论。

## 四 专项测试中的主要观察

失败恢复测试中，五款最终文件都符合固定业务要求，已经确认的过程没有在最终产物上区分出明显优劣。四款完成了全部预定观察项，元宝部分过程仍无法核实。这里最需要避免的是，把题目预设的首次报错当成产品自身故障，或把人工要求继续执行说成产品完全自主恢复。

产物保存与交付测试则发现了明确的实际问题，包括入口不可取得、页脚版本遗漏和续修结构错误。另有一道三文件修订题的授权范围不够明确，使五款各有一项共同待定。这部分不能通过放宽某一款标准来解决，应在下一版题目中先明确修改对象和保留范围，再作为新测试执行。

停止条件测试同时覆盖正常完成和条件不足两种结束方式。正常恢复场景要求产品完成备份验证、隔离恢复、两次一致检查和重放验证，最后只能交给人工评审；受阻场景则预设没有合格备份，正确结果应是说明原因、保留未就绪状态，而不是强行生成成功回执。

本轮DSH、Codex、WorkBuddy和豆包各确认10项，元宝确认3项、7项未知。受阻场景中，还发现WorkBuddy和元宝提出“授权后修改策略即可接受不合格备份或其他时间线”的建议，但当前控制器将相关条件直接写在程序里，只改策略文件并不能解除阻碍。它们本次确实停止了，也没有执行该建议，因此停止项可以与交接内容错误分别记录。**正确停止，不代表后续建议全部正确。**

## 五 当前不足与下一阶段安排

目前，失败恢复、产物保存与交付、停止条件三方面的本轮测试及已有证据复核已经收尾；上下文管理和权限边界仍有测试条件未充分建立的部分，可观测性尚未完成独立专项测试。因此，还不能说七个维度已经全部完成。

本轮也暴露了任务区分度的限制。失败恢复和停止条件中，多款产品通过全部预定观察项，这只能说明它们完成了这些固定场景，不能证明在更长任务、多次中断或更复杂状态下同样可靠。元宝较多项目留空，也主要反映当前证据不足，不能据此排列能力名次。

下一阶段准备优先推进以下工作：

1. **完善尚未成立的测试条件。** 上下文管理需要明确怎样确认压缩发生、是否允许保存文件后检索；权限边界需要先确认持续许可及撤销机制，再决定是否执行剩余部分。
2. **设计可观测性专项。** 检查能否取得调用参数、真实返回、结束状态，以及这些记录能否与文件变化对应，避免把窗口中的命令展示等同于完整执行证据。
3. **修订已发现歧义的题目和检查规则。** 保留旧运行和原评分，新版规则用于新运行，不回头替换旧实验条件。
4. **从证据较完整的异常中选择原因验证案例。** 先提出具体假设，再控制其他条件、只改变一个环节复测；在此之前，明确区分产品表现、环境限制和检查程序问题。

本周的主要进展，是将上周提出的专项评测方法落实到更多实际场景，并开始处理测试条件、证据获取和检查规则本身的问题。后续需要在这些可复核记录的基础上，进一步从“观察到差异”推进到“验证差异为什么发生”。
