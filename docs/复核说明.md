# 怎样核对已有记录与评分依据

最新统一运行简表见[总索引](../results/unified-runs-2026-10-30/总索引.md)，七维比较资格见[审阅汇报](阶段进展/七维审阅汇报-2026-10-30.md)。以下保留历次检查范围，具体新增检查见文末。

## 为什么提供这个程序

结果表中的分数，需要能追溯到实际调用、返回或文件。例如，“长报告保存准确”应当有保存文件与预期报告的比较，不能只依据产品回复“已经保存”。仓库提供[checks/verify.py](../checks/verify.py)，把部分可以用代码完成的核对步骤保存下来，方便重复检查。

它读取已有文件，按写好的条件检查材料是否相互一致。它不会打开受测产品、调用模型、执行输入程序或生成新的运行结果。缺少必要现场的条目仍保留未知，不能靠程序补出通过结论。

## 怎样运行

使用Python 3.9或更新版本即可，不需要安装第三方库。进入包含README.md、cases、results、evidence和checks的仓库根目录。

核对全部已有记录：

```bash
python3 checks/verify.py
```

这条命令检查60项信息回传记录，以及五款上下文基础题。60项是记录中的观察项数量，不是60次产品运行，也不表示60项都已获得充分证据。

只选择WorkBuddy在FB03「截断后完整结果获取」中的第四项“全文保存准确性”：

```bash
python3 checks/verify.py --item WB-FB03-04
```

`--item`用于指定观察项编号。这里`WB`代表WorkBuddy，`FB03`代表截断后完整结果获取，`04`代表第四项。程序会检查这一项的评分来源和所属现场组，同时仍核对仓库全部文件指纹和各产品的汇总额度；这次不会检查五款上下文题。

## 它实际比较哪些材料

| 检查内容 | 比较对象 | 能回答的问题 |
|---|---|---|
| 文件是否变化 | 实际文件与[MANIFEST.json](../MANIFEST.json)中的大小及SHA-256 | 文件是否与清单记录一致；SHA-256是文件内容的指纹 |
| 分数是否对应 | [逐项记录](../results/information-feedback.json)、历史评分来源和汇总额度 | 单项分数是否与来源一致，未知或待补部分是否仍被保留 |
| 工具返回是否一致 | 有归档的调用与返回、程序为评测方保存的预期回执 | 调用是否配对，实际状态和指定字段是否符合相应检查条件 |
| 全文是否准确保存 | 产品保存文件与本次预期报告 | 文件字节是否完全相同，差异能否由额外回车解释 |
| 三轮要求是否正确更新 | 可见问答、实际提示词及最终四字段 | 顺序是否正确，第三轮是否未补答案，最终记录是否符合有效要求 |

预期回执是测试程序为评测方保存的参考结果。它需要与产品实际返回或保存文件对照；仅有回执不能证明产品收到了信息。日志里的原临时入口只作为文字参与配对，程序不会访问这些路径。文件清单本身不记录自己的指纹，以免产生循环引用。

## 运行成功该怎么理解

以WorkBuddy的全文保存项为例：预期文件262144字节，实际文件264202字节，多2058个回车字符；移除回车后与预期正文一致。核对程序确认这些关系符合现有文件和记录后，会正常结束。产品按运行前的严格字节保存规则仍得0分，因为原文件没有逐字节保持一致。

所以，需要分别看材料核对是否完成，以及记录中产品各项的得分和证据状态。终端结束状态0表示程序列出的核对条件满足；状态1表示出现不符，错误信息会指出原因，例如文件指纹变化或字段不一致。

程序会输出JSON，即按字段组织的文本。几个主要字段可以这样读：

| 输出字段 | 含义 |
|---|---|
| public_files_checked | 本次核对指纹的文件数量 |
| feedback_judgments_checked | 本次检查的信息回传记录数量；指定单项时为1 |
| feedback_states | 各类证据状态的条目数，包括通过、未通过和未知等 |
| groups | 对应现场组的核对说明及仍保留的限制 |
| context_products | 五款上下文基础题的结果；指定信息回传单项时为null，表示本次没有检查这组题 |
| historical_positive_points_waiting_for_raw_evidence | 所选记录中，历史正向分仍待补现场的分值 |

例如，`supported_negative`表示有证据支持产品该项未通过；`insufficient_evidence`表示证据不足、无法判断。完整状态定义见[打分与证据规则](打分与证据规则.md)。

## 哪些结论不能由程序确认

对于元宝信息回传、豆包部分历史正向或待查项，必要工具正文不足，程序只核对现有记录来源和证据状态。正常结束不表示这些条目已经通过，也不表示证据缺口补齐。

仓库使用经路径替换的事件摘录，程序不能据此确认完整模型请求、未公开事件或内部组件责任，也没有验证长上下文压缩和多次运行的稳定性。保留在历史评分JSON中的validations/checks字段，记录的是当时本地检查；这次没有重新执行全部旧检查，例如原始ZIP与完整日志的一致性及截图像素核对。

## 另一个程序检查什么

```bash
python3 checks/check_package.py
```

这条命令只检查仓库文件的常见整理问题：Markdown文档链接及其章节定位是否存在、是否还包含未替换的本机路径、是否命中列出的常见密钥和邮箱格式。它不检查产品成绩，不访问外部网页，也不保证发现所有个人信息。

## 文件改变后怎样处理

若出现指纹不符，先查看具体文件，判断是否发生了有意修改。即使只是修改文档，也应确认内容后再更新清单；更新指纹本身不能证明评分判断正确。如果修改证据或规则，还需要同步检查来源说明和核对代码，并保留旧版本。

下载或运行过程中产生的.git、.DS_Store和__pycache__等元数据会被忽略。实际执行记录见[材料核对记录](../checks/整理检查结果.md)。
