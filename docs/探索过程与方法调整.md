# 探索过程与方法调整

## 最初的想法

我最初希望通过公开任务发现Harness问题：选择真实办公题，让五款产品执行，再从失败中寻找原因。公开题有业务背景和既有评分程序，能够帮助判断交付文件是否满足要求，也能让我熟悉各产品的操作方式。

因此，前期主要在筛选题目、检查附件和评分程序、准备运行环境，以及整理各产品的输出。这些步骤有必要，但随着候选题增加，我发现自己花了较多时间确认“题目能不能测”，却没有尽早回答“它具体测哪项Harness能力”。

## 为什么增加题量没有直接解决问题

复杂任务混合了多种能力。例如，财务模型补全既要理解业务含义、计算公式，也要保留工作簿内容、使用工具并保存文件。最终数值错误，可能来自其中多个环节。即使取得一个失败分数，也未必知道接下来应该检查哪个执行环节。

评分程序本身也需要核对：题面是否说明了检查器要求的固定位置？公式是否需要重新计算后才能比较？原文件中已有错误是否属于本题修改范围？如果这些条件不清楚，产品得零分也不能直接当作有效的失败案例。

这些经历让我认识到，更多测试不一定带来更清楚的原因判断。前期已有评测维度，我应该更早把它们转成可以观察和判定的具体问题。公开任务适合发现异常，但需要专项测试进一步检查这些异常。

## 怎样把标准变成测试

以信息回传为例，我先把问题拆开：正常状态和错误状态是否准确返回？较长结果中指定字段是否保留？输出被截断时，产品有没有说明、有没有提供完整入口？入口能否实际读取，保存文件是否一致？

再为这些问题设计输入程序、提示词和检查方法。[FB03「截断后完整结果获取」](../cases/FB03/README.md)固定生成256 KiB模拟报告；先保留首次返回，之后才按人工指令读取入口。实际返回与本次报告的随机编号、核对标记和完整文件相互比较，避免混用旧结果。

这样，一次运行可以回答更具体的问题：首次有没有入口，后续能不能读取，保存字节是否一致。它减少了业务计算对结果的影响，但不同模型仍会选择不同工具，产品环境也不同，所以还不能把全部差异归到Harness某个内部组件。

## 评分过程中继续修正认识

以下三个情况让我进一步明确了证据的用法，具体记录见[信息回传逐项结果](../results/information-feedback.md)。

**第一，要先确认目标情况确实发生。** WorkBuddy基础题的错误模式在保存回执时提前退出，预设错误字段尚未生成。这里的回执是测试程序为评测方保存的预期结果。既然目标字段没有生成，就不能把未看到字段解释为产品丢失信息，因此相关项留作未有效测试。

**第二，要按观察对象判断证据够不够。** 元宝信息回传缺少必要的工具正文，无法判分；但[多轮要求更新](../results/context-update.md)检查的是实际对话中的最终四字段，同一分享页的连续问答能够支持这项核对。后台日志不是所有任务的共同评分前提。

**第三，已有分数还需要对应的原始现场。** 豆包历史确认分值中有5分缺完整现场。整理时保留原分数，同时单列证据缺口，不能因为过去判过分，就写成现在已经能够充分复核。

## 下一步怎样使用两类任务

后续我会先用专项任务检查明确的执行行为，再通过真实业务任务观察这些行为是否影响交付。专项题可能遗漏实际使用中的问题，业务题则可能混合多种原因，两者需要互相补充。

如果新证据说明标准或用例需要调整，应保留旧版本，说明修改原因，再开展新测试。下一阶段先确定其余维度用例，并完成各维度运行和评分；在这之后，再选择有充分原因线索的失败，保持任务、模型和评分方法不变，只改一个执行环节进行对照。目前还没有量化结果证明这次方法调整节省了多少时间，或提高了多少原因判断准确度。
