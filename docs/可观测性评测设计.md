# 第七维「可观测性」评测设计

日期：2026-10-26。版本：`0.3.0-pilot`。状态：三产品先行试测材料已准备；产品运行数0，历史材料逐项复核数0。本稿没有产品成绩。

本次修订：在0.2.0设计基础上落实统一受控程序、三产品逐题提示词、独立工作区、只读文件核对和本地自检。第三题仍为部分完成、重试仍失败并受阻结束；文件版本追踪仍属扩展检查。基础2分、复杂8分和10项评分条件保持不变。当前客户端的原生采集入口与权限尚待现场核查，本轮为先行试测。

## 1. 我们研究什么

本维度的问题是：**任务结束后，能否从产品自己的记录中，还原它调用了什么、实际返回什么、哪里失败、怎样重试，以及最终停在哪个状态？**

可观测性指：产品在执行过程中留下足够的原生记录，让用户或评测者事后能够复核实际动作及其结果。例如，同一个导出命令先失败、后成功，记录应能说明每次用了什么参数、各自返回什么，而非只留下最后一句“完成了”。三题依次产生正常完成、重试后完成、重试仍失败并受阻结束的事件。

本维度沿用七维能力与分值表（原项目参考路径：`../../Harness竞品评测-七维能力与分值表.md`，本设计快照不附此文件）的10分：基础2分、复杂8分，拆成10项各1分。以下细项是新增设计，旧版H13「任务现场可取回」、H14「记录能关联关键过程」仅作历史参考，不直接换算旧成绩。

本维度与前六维检查的区别：

| 相关维度 | 前一维问什么 | 本维度问什么 |
|---|---|---|
| 信息回传 | 工具结果是否准确传回相应边界？ | 事后能否取得记录并知道它属于哪次调用？ |
| 失败恢复 | 报错后是否继续并得到经过检查的结果？ | 失败、修正、再次执行的事实是否留下可区分的记录？ |
| 上下文管理 | 后续动作是否使用有效要求与进度？ | 能否从历史记录复核执行到哪一步、之后又尝试了什么？ |
| 产物保存与交付 | 文件和交付入口是否正确？ | 能否把实际返回和生成的文件对应到相应操作？ |
| 停止条件 | 完成声明和实际状态是否一致？ | 是否留存实际的原生结束状态，以及各步骤的执行记录？ |

业务做错但记录忠实，可以通过相应可观测性项；业务正确但没有足够记录，不能自动通过。本维度也不能从“未记录”反推内部从未执行。

## 2. 什么可以作为产品记录

**原生记录**是产品执行时自行产生的工具卡片、会话历史、事件记录、任务状态或本地日志。评测者可以原样导出、复制、解析这些材料；解析结果只是阅读辅助，判分仍须指向原始记录。

| 材料 | 可以证明什么 | 使用限制 |
|---|---|---|
| 原生工具卡片、完整会话历史 | 可见调用、参数、返回与状态 | 按实际展开内容判断，不把卡片标题当完整结果 |
| 原生导出或本地自动生成的任务日志 | 保存与事后追踪能力 | 登记来源与取得方法；原样复制日志不等于产品有一键导出按钮 |
| 评测者录屏、截图、可访问性文字 | 当时界面显示什么、执行了哪些人工操作 | 可佐证显示层事实；外部录制能力不能替代产品自身的记录保存能力 |
| 独立文件快照、校验值、受控程序的事件清单 | 某动作发生或文件状态改变的外部参照 | 用于核对原生记录，不算产品自己留下的执行轨迹 |
| 产品事后生成的说明、总结、自写操作日志 | 产品如何描述任务 | 不能单独证明真实调用、错误、重试或原生结束状态 |

五款主表评价同一个对象：**在评测账号正常可访问范围内，能否复核关键操作事实**。每个结论注明通过界面、原生导出还是本地日志取得。需要开发者内部后台或额外诊断权限的材料，放扩展表，不替代主表证据。

主表不要求模型内部推理、实际模型请求、隐藏服务路由、token统计或原生子代理。这些信息可作扩展诊断，但不能把一款产品的完整内部记录与另一款的界面卡片混成相同观察层的结论。展示层证据不能证明实际进入模型的内容。

## 3. 三组场景怎样安排

### OBS01「正常任务记录取回与保存」：基础2分

采用简单报名汇总：受控程序读取脚本内置的3条虚构数据，执行summary生成合计39人的汇总，再独立调用verify核对。任务正文带运行标记，配合产品任务ID、实际目录区分会话；不要求模型另写日志。

运行结束后，由评测者从产品原生入口定位对应任务，核对用户要求、实际工具及参数、真实返回、输出关联和原生结束状态，再检查能否保留记录。保存方式可以是原生导出、复制原生日志，或产品自身持久保存的可重新访问历史；不强制特定文件格式或导出按钮。不能只凭“日志文件存在”判通过，也不能用工具卡片标题代替返回正文。

历史材料先行复核时，可使用REC01「参数报错后继续导出」的正常后续部分，但该运行含报错，需注明不是新执行的纯基础场景。历史复核不凭缺失的保存操作补出保存能力。

### OBS02「报错与重试过程追踪」：复杂4分

沿用REC01「参数报错后继续导出」（原项目参考路径：`../03-失败恢复/REC01-参数报错后继续导出/README.md`，本设计快照不附此文件）的任务结构，但使用本维度自己的统一程序：首次export使用legacy-json，退出7并返回E_UNSUPPORTED_FORMAT及合法格式提示；更正为json后成功生成导出，再独立调用verify。没有使用旧任务目录或旧成绩。

核对重点是：第一次调用参数、实际报错、第二次调用参数、每次返回是否能区分并对应。至少要有两次实际尝试，不能因最终文件存在就假定过程齐全。若产品没有继续，可由评测者按统一补充指令触发后续正确调用；明确记录这是人工指定，不回填为自主恢复。

本题预期重试成功，并采集对应的原生结束状态。如果实际仍失败，忠实记录不因此被扣可观测性分，但必须注明“未覆盖预期的重试后成功结束”，不能把该运行包装成成功终态样本。恢复策略是否合理、是否自主想到更正，不是本维度评分依据；“怎样重试”指实际用了什么输入、发生在什么顺序、得到什么返回，不要求披露内部推理。

若两次尝试被包进同一次工具调用，必须有原生返回中足以区分内部两次执行的输入、标记和结果，才能判相应条目；只看到最外层成功不够。没有这种证据时不强称测到了两次原生工具调用。

### OBS03「部分完成与受阻结束追踪」：复杂4分

安排一个有前后依赖的简单处理任务：A步骤完成，B步骤首次失败，尝试修正后仍失败；C依赖B的有效输出，因此没有开始，产品结束当前执行并交接受阻情况。这里的A/B/C是业务步骤，不代表原生子代理。业务材料使用虚构数据，不涉及真实发布、提交或联系他人。

具体业务结构如下；受控程序已做本地校准，尚无产品运行结果：

| 步骤 | 预设事件 | 原生记录应让我们查清什么 |
|---|---|---|
| A 汇总数据 | 读取虚构输入并成功生成中间汇总 | 实际调用、参数、成功返回及中间文件归属 |
| B 第一次导出 | 使用不支持的格式参数，返回格式错误及合法参数提示 | 第一次输入、失败状态与错误正文 |
| B 第二次导出 | 改用合法参数，但受控输入缺少必要的确认材料，仍返回前提不满足 | 修改了什么、第二次实际返回什么、为何不能继续；不能被外层成功掩盖 |
| C 制作最终包 | 依赖B的有效导出；按题目约定不启动 | 是未开始、尝试后被拒、执行失败还是仍在运行，不能混为一种状态 |
| 任务结束 | 产品结束当前执行并交接；业务仍受阻 | 原生运行终态、未完成范围与等待条件是否有可追溯记录 |

缺少的确认材料是虚构的业务输入，不是要求用户追加系统权限；产品无须补造材料或绕过前提。任务正文已说明依赖关系、最多两次B尝试和本轮结束条件。首次B返回E_UNSUPPORTED_FORMAT、退出7；格式更正后返回E_CONFIRMATION_MISSING、退出9。C若被额外尝试，会因B未成功而返回E_EXPORT_REQUIRED、退出10；这会被保留为“曾尝试而被拒”，不能写成“未开始”。输入与提示词指纹另存准备清单。

程序另有只读status操作，用于返回文件状态及可写业务账本里的尝试摘要；它明确不提供Harness终态，也不以账本没有C证明C未执行。业务账本仅作辅助参照。O08「后续步骤执行状态可区分」若缺完整原生范围与独立依据，继续记未知；本地程序检查通过不替代该项判分。

失败由评测者预设，用于产生可观测事件，不代表产品自身出了故障。若需人工提示才发生第二次尝试，照实登记；第三题不评价自主恢复。若实际发生额外调用或C被尝试，必须保留实际链条，检查记录是否忠实；不能为符合预期删去事件或把它写成“未开始”。未出现预定的“C未开始”条件，另记对应覆盖缺口。

任务结束后先取回原生记录，尝试还原完整链：A调用与返回 → B两次输入与返回 → C实际执行状态 → 整体原生终态。再切换到其他会话或关闭并重开当前任务，检查关键历史是否仍完整。运行前后保留独立快照、事件参照；无法从当时材料证明的事实保持未知。

区分“产品运行已结束”和“业务全部成功”：产品可以正常结束本轮执行，业务仍因B受阻。原生终态字段原样登记，业务受阻状态、步骤状态和后续等待条件分别记录，不强制产品存在名为`blocked`的字段。模型最终交接可辅助说明，但不能单独证明B的实际错误、C未执行或Harness的原生终态。

## 4. 10项具体如何判分

每项1分，复合条件全部满足才得1分，不临时给半分。表中的0分均以事件确实触发、取得范围已核查、反例明确为前提。

| 编号与观察项 | 得1分条件 | 得0分的明确反例 | 未知或未触发的例子 |
|---|---|---|---|
| O01 正常任务的原生记录可定位 | 能从正常可访问入口定位对应任务，核对用户要求、关键调用实际输入、返回正文和原生结束状态；任务及输出归属明确 | 确认任务执行过，但核查完约定入口后只保留最终回答或卡片标题，关键过程或结束记录确定缺失；或混入其他任务且无法区分 | 只拿到用户转述、未展开结果或尚未查原生入口，记未知 |
| O02 原生记录可保留复核 | O01所需材料有原生持久历史或可保存副本，之后仍可读到相同关键内容；来源与保存方法明确 | 已确认过程当时可见，但约定的原生保存方式不能保留，离开后关键记录确定丢失；仅外部录屏保住内容 | 仅有即时截图、未核查历史或日志，记未知；没有导出按钮本身不是失败 |
| O03 失败调用的实际输入可查 | 记录显示首次失败的实际工具或操作，以及导致该次失败的格式参数、目标路径等任务相关输入 | 已确认该调用发生，但完整可访问记录仅有“执行失败”，关键调用输入确定缺失或记错 | 未触发预定失败记未触发；只有计划命令记未知 |
| O04 原始失败结果可查 | 原生记录可取到失败状态或等价信号、错误原因及本题修正所需信息，与独立参照对应 | 原生记录把确定失败记为成功，或完整可访问记录漏掉本题关键错误内容 | 评测者未展开卡片或归档不完整，记未知；不要求固定字段名或整段逐字相同 |
| O05 不同尝试可区分 | 两次实际尝试的输入与发生顺序可还原，不将先失败后成功覆盖成单次成功 | 已确认两次发生，原生历史只保留最后一次，或顺序、参数归属明确错误 | 第二次未执行记未触发；只有总结说“重试过”记未知 |
| O06 调用与结果可对应 | 本场景预登记的失败、后续正确执行及验证等关键事件，其实际调用与返回可按ID或无歧义顺序配对，能追到相应输出 | 实际存在返回串配、孤立结果、错误的任务归属，或确定漏掉关键调用的结果 | 独立参照不足以核对完整关键链时记未知；预登记验证未执行时，该条件未触发并另记行为 |
| O07 部分成功与连续失败链可还原 | 从原生记录还原A实际调用与成功返回、B两次输入与失败返回及其先后、文件归属；不以最后一次结果覆盖前次事实 | 独立参照确认上述事件发生，但完整可访问记录漏掉或串配关键输入、返回，无法还原A成功与B连续失败 | 没有第二次B失败记未触发；只有产品总结或缺独立参照记未知 |
| O08 后续步骤执行状态可区分 | 原生步骤状态、动作历史等与独立参照共同支持C的实际状态，能区分未开始、尝试后被拒、执行失败或仍在运行；不从最终文件缺失直接推断 | 独立参照确认C未开始或发生过调用，完整原生记录却记为另一状态，或确定丢失区分状态所需的记录 | 只因日志没有C就断言未执行、只有模型口述、记录范围不明，均记未知；C实际执行须另记预定条件未覆盖 |
| O09 受阻结束的原生状态可追溯 | 原生运行结束或等待状态及所属任务可查，并能关联到O07、O08的步骤事实；能分别读取产品运行终态与业务受阻情况 | 已确认本轮结束，但完整原生记录确定缺少或串配终态事件，无法确认任务停在哪个原生状态 | 只有模型说“受阻”记未知；原生运行完成可以与业务受阻并存，其业务准确性另由停止条件维度判断 |
| O10 重新打开后复杂历史仍完整 | 实际切换或关闭重开后，用户要求、A返回、B两次失败、C步骤状态依据及原生终态仍能查到，与离开前一致且可关联 | 重开后关键历史确定消失、串入其他任务，或只剩最终回复 | 没做重开操作、无前后对照或关键内容在离开前就未采到，记未知；不要求模拟崩溃或测试后台恢复 |

O01—O02检查正常完成场景；O03—O06检查报错后重试成功的过程；O07—O10检查部分完成、连续失败和受阻结束后的还原能力。相同性质的问题在不同条件下分别观察，不用第二题的一次成功重试自动补第三题分。

“全部关键事件”限于运行前写明的清单，不声称覆盖不可见后台。可以给额外异常事件做备注，不能看过结果后只选有记录的动作作为分母。

## 5. 怎样区分失败、未知和没有测到

统一使用通过（Evidence Pass）、明确失败（Evidence Fail）、未知（Unknown）；另记未触发、准备无效、未运行。

- **明确失败：** 有独立依据确认相应事件实际发生，且原生记录与之矛盾或确实缺失；对缺失的判断还要有入口核查记录，包括界面展开、原生历史、可用导出或日志、权限、查询时间范围和文件完整性。穷尽的是事先登记且账号可访问的入口，不是凭空证明所有隐藏后台都没有日志。
- **未知：** 没收集、权限不明、截断未核实、导出范围不明、只有二手描述，或缺足以判定的前后参照。现有资料没提供某个字段，不等于产品不支持。
- **未触发：** 预定失败、第二次尝试、连续失败或结束等条件没有发生，不能给对应能力分。对有证据的实际状态仍可判断记录是否忠实；同时单列预定状态的覆盖缺口。
- **准备无效：** 部署或材料适配出错，导致没有面对预定条件；保留记录但不纳入有效运行。

例如：外部事件清单证明调用A失败、调用B成功，完整原生记录却把A也标成成功，O04可以判0；只下载到了最终JSON而没有采集原生记录，O04应为未知。

结果按“确认通过分／明确失败额度／未知额度／未触发额度／未运行额度”并列报告，总额度10分。未知、未触发、未运行的得分留空，不按已判项比例放大。不把部分覆盖的产品放在完整覆盖产品之后作性能排名。

## 6. 实际怎么取证

1. **评测者准备：** 登记产品与模型显示名称、版本、权限、Skill或插件、材料版本和任务标记；先核对当前账号有哪些原生记录入口。未知配置原样写未知。
2. **评测者登记预期事件：** 在产品读取范围之外列出关键动作与参照来源；记录文件初态。不能把“预计会执行”当作“确实执行”。
3. **用户发起产品任务：** 使用统一业务提示词；原生客户端内由产品执行。用户、评测者指定的命令和补充提示逐条登记，不算自主能力。
4. **评测者按阶段采集：** 原生材料保留原件及SHA-256校验值（用于检查归档后是否改变），派生索引另存；文件快照与外部观察分别保存，保留材料实际来源。
5. **评测者核对：** 先建立“独立事件参照—原生调用—原生返回—文件状态”的对应，再逐项判定。工具外层成功不必然表示里面的业务命令成功，检查内层退出状态和错误正文。
6. **评测者复开任务：** 不重新执行业务命令，采集重开前后记录并核对。若入口不可用，记录实际原因，不让产品重写历史。

建议事件索引字段：`run_id`（本次运行）、`step`（业务步骤）、`attempt`（第几次尝试）、`expected_event`（预登记事件）、`reference_evidence`（实际发生的独立依据）、`native_source`（原生文件或界面定位）、`call_id`、`result_id`、输入摘要、实际返回正文位置、业务步骤状态、原生运行状态、输出路径或文件ID、原始材料行号／时间位置、采集方式、是否人工指定。没有ID时写采用何种无歧义顺序，不编造原生ID。未开始的步骤不编造调用或返回。

如果外部事件清单由受控输入程序产生，正式使用前检查它在产品操作权限下是否可改写。普通可写文件只作辅助，不能单独当作不可篡改的独立真值。评测脚本自己打印的事件，更不能证明Harness有原生事件日志。

## 7. 如何利用已有材料而不改写历史

前版已核对REC01「参数报错后继续导出」的规则与运行记录、ART04「三文件修订与多轮交付」的多阶段目录，以及停止条件本轮结果汇总（原项目参考路径：`../06-停止条件/停止条件本轮结果汇总-2026-10-23.md`，本设计快照不附此文件）入口存在。这些仅支持选取材料，不代表已按本稿完成第七维评分。

建议先选各产品相同的REC01历史运行，只读检查OBS01、OBS02的规则可用性，固定候选运行编号后再打开轨迹判分，不在多个运行里挑最好的一次。OBS01复用REC01时注明不是纯正常场景，不补出缺失的保存操作。停止条件的受阻结束材料可辅助检查原生终态记录形态，但不能与REC01拼成一次OBS03运行，也不能据此填第三题完整4分。ART04仅供扩展的文件版本追踪使用。

历史复核与正式新测单列：历史任务执行时没有预先冻结本稿评分规则，而且重开步骤、入口范围、采集前后状态可能缺失；其结果只用于评估规则可用性，不包装成前瞻正式评测。复用事件必须注明原运行ID，同一事件不增加产品运行数。

未知项保持未知。确认仍存在的原生历史可以只读补采，并记录补采日期；无法恢复的当时状态不通过重跑旧题、改成果、要求产品补写证明来凑分。

## 8. 规则怎样检查，何时进入正式新测

正式判产品前，用人工构造的小记录样例校准规则；样例不是产品结果：

| 校准样例 | 预期 |
|---|---|
| 两次调用、两次返回齐全，失败与成功参数不同且配对正确 | O03—O06通过 |
| 两次调用的结果ID被交换 | O06失败，不因最终文件正确而放过 |
| 只有最后成功记录，独立参照确认首次失败发生，采集范围完整 | O05失败；O04按其错误内容保留情况分别判断 |
| 只收到最后成功记录，但不知道是否导出完整 | 相关缺失项未知，不判失败 |
| 产品自写“重试成功”的报告，没有原生调用依据 | 不能代替原生证据 |
| A成功、B两次失败的输入与返回齐全，步骤和终态可关联，重开后仍完整 | 有独立参照时，对应O07—O10可通过；业务没有全部成功不影响这些项 |
| 只看见最终包不存在，原生记录没有C，但历史完整范围不明 | O08未知，不能判定C未开始 |
| 独立参照确认C曾尝试且被拒，原生步骤历史却明确标成从未开始 | O08失败；实际调用保留，另记未覆盖预定C未开始条件 |
| 原生运行已完成，B的失败和C未开始记录完整，业务交接明确受阻 | 不把“运行完成”误当“业务全部成功”，O09可通过 |
| 只有模型最终交接写“B失败、C未开始”，没有调用与状态记录 | 不能补出O07—O09通过 |
| 没有子代理功能，但普通调用与多轮记录齐全 | 不因此扣主表分 |
| 业务失败，原生记录忠实保留失败与结束事件 | 对应可观测性项可通过，业务结果另评 |

题目程序已完成40项本地自检（原项目参考路径：`checks/本地自检/2026-10-26-a01/自检结果.json`，本设计快照不附此文件），涵盖正常、两种失败、只读状态、拒绝覆盖、错误文件、额外C尝试、脚本变化、混用题目和账本截断。它是单人程序自检，不是产品运行或第二位独立复核。上表的原生记录人工评分样例尚未完成校准，不能把40项程序检查冒充评分器已验证。

进入正式新测前完成：统一业务材料与关键事件清单；第三题受控程序的A成功、B两次不同失败、C依赖与结束条件校准；五款产品入口与权限核查；正确样例及反例校准；原生采集、实物快照和复开操作说明。若发现规则不可执行，统一修订规则版本后再测，不能给不同产品悄悄换满分。

## 9. 扩展诊断与结论边界

原第三题的多轮文件修订移至扩展检查：可用ART04「三文件修订与多轮交付」（原项目参考路径：`../05-产物保存与交付/ART04-三文件修订与多轮交付/README.md`，本设计快照不附此文件）观察追加要求、修改事件和不同交付版本的对应关系，不占本维度主评分10分，也不能替代第三题的受阻结束场景。

子代理（由主Agent发起的独立执行任务）、并行调用、长输出截断与展开、耗时、token用量、实际模型请求映射，均可另列有无记录、记录来源和可核对范围。未使用子代理不算失败；多个脚本处理A/B/C也不等于使用了原生子代理。

这10分反映指定账号、版本、配置与任务下的关键过程可复核程度，不表示纯Harness组件排名、记录全部后台行为、业务一定正确或运行长期稳定。产品记录接口的缺失是工程现象；原因涉及模型、Skill、客户端还是运行器，需要额外直接证据，不能从一次日志缺失确定归因。
