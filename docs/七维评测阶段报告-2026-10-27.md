# 面向 Agent 的 Harness 能力评测与故障归因：七维阶段报告

截至2026年10月27日。阶段：五款原生产品先行试测与证据整理。原生产品指使用产品本身的客户端、模型和工具配置。

## 1．这阶段要回答什么，已经推进到哪里

我们研究的是：一个 Agent 在调用工具、保留任务要求、处理失败和交付文件时，外围执行系统能提供什么支持，以及出现问题后能否从记录中查清发生了什么。这里把组织模型、工具、任务状态和权限的系统称为 **Harness**；模型负责理解和选择操作，产品自带的技能说明（Skill）也可能影响操作。因此，看到某款产品一次做得好或做得差，还不能直接认定是某个 Harness 组件造成的。

前期工作按七个维度逐题展开，留下了题面、评分规则、产品记录和各维度报告。这样能分析单题，却不容易整体回答“测到哪里、哪些结果可确认、哪些还缺证据”。本阶段因此先完成五款×七维总表和统一运行台账，再据此整理本报告，同时检查比较条件与未知项去向。

**当前成果是可追溯的阶段性结果，还没有形成公平的100分排名，也没有完成一个产品执行缺陷的原因验证与修复闭环。** 七个维度都有工作材料，但上下文管理的复杂16分仍未正式覆盖，权限边界也未建立五款共同条件。这两个缺口不妨碍报告已有结果，但必须保留在结论中。

## 2．我们怎样测试和判定

### 先固定要观察的行为，再对照实际证据

七维额度来自本项目的能力与分值设计（完整原件留本地），不是论文规定的标准。用例同时包含自编固定程序和公开工作流的适配。固定数据、命令与故障，是为了减少业务计算和开放式规划的干扰；公开办公、档案与模拟恢复任务，则用于观察较长工作流中的文件、交接和结束行为。它们仍是原生客户端先行试测，不能称为官方完整环境复现。

每道题尽量在运行前写明输入、规则和观察项。用户负责在产品中发起任务，并完成需要的批准或明确续做步骤；评测助手准备材料、读取归档和核对结果。人工指定的第二阶段读取、暂停后继续、手动压缩和批准，都记录为实验安排，不算产品自主发现或自主恢复能力。

判定时区分三种主要状态：**确认通过**是证据支持满足既定要求；**明确失败**是存在相应反例；**未知**是证据或规则解释不足。预设场景没有成立则记“未有效测试”，尚未完成正式题目则记“未正式覆盖”。例如程序在保存回执时提前退出，就不能拿它评价原先安排的错误字段回传；未知也不能按0分处理。

### 文件、工具返回和产品状态分别看

同一个任务至少可能涉及以下几层证据，它们回答的问题不同：

| 证据 | 可以支持什么 | 不能直接推出什么 |
| --- | --- | --- |
| 实际下载件或工作区快照 | 文件内容、版本、结构以及前后是否相同 | 当时执行了哪条命令，或模型实际收到了什么 |
| 原生工具调用和返回 | 实际参数、返回内容、报错与重试顺序 | 所有日志字段都进入了模型请求 |
| 产品界面自身的任务收尾显示 | 该界面层的结束或等待状态 | 隐藏后台的全部进程状态 |
| 用户按具体要求完成重开的直接反馈 | 用户实际观察到的界面历史保留 | 评测者亲眼看到了界面，或仅凭文件相同证明发生过重开 |
| 模型最终回复、普通业务账本 | 产品的声明和辅助业务记录 | 独立的原始返回、不可改写的监控或原生任务终态 |

因此，短对话题可以通过连续问答核对最终值，工具回传题却必须检查实际工具结果；不同证据要求本身不构成判分不一致。我们需要检查的是：**同一观察项是否对不同产品使用了相同条件和要求，以及报告有没有把较弱证据说成较强证据。**

核对副本时，我们使用SHA-256文件指纹，即根据文件字节内容计算的摘要。相同指纹支持“所比较的文件内容一致”，不能单独证明文件来源真实、模型读过全部内容或实际执行过某条命令。

有三个具体例子能说明，为什么分数需要连着证据解释。

**Codex的完整结果入口缺口是已观察现象，但底层保存仍未知。** FB03「完整结果获取」首次原生返回声明了截断，却没有提供可用完整入口，因此“提供入口”和“按入口取回”两项失败；没有入口不证明底层一定没存全文，所以“完整保存”仍未知。这几项来自同一事件，不能再算作多个独立故障。信息回传结果解释（完整原件留本地；[公开维度摘要](../results/information-feedback.md)）保留了这个区分。

**DSH的页脚问题不能直接归为保存工具丢失内容。** ART04「三文件修订与多轮交付」中，末页标签已更新，但112页页脚仍旧。既有页脚失败分析（完整原件留本地；[公开维度摘要](../results/artifact-delivery.md)）显示：可见检查已经读到旧页脚，修改范围判断将页脚排除，保存后读取仍是旧版，自检也没有覆盖页脚。这个链条支持“修改范围判断与验收覆盖不足”，没有观察到正确页脚版先生成、再在保存时消失。任务授权描述的歧义也可能影响选择，内部唯一原因尚未验证。

**可观测性通过可以包含业务失败或预期受阻。** 旧WorkBuddy正常任务因目录异常未完整完成，但这次失败本身留下了调用与返回；它不能充当新版正常完成覆盖。新版第三题又是刻意设计的部分成功、连续失败和受阻结束，评价重点是记录能否还原，不是要求它把缺失输入伪造出来完成业务。旧输入、新输入和诊断任务在台账分别保存。

## 5．未知怎样处理，哪些不再追查

本次把当前未知、历史正向待证、待核验、未有效测试和正式覆盖缺口分别登记。每条都有原观察项、缺失内容、是否可能从同次任务补取、下一步及停止条件，见[逐项清单](未知项与覆盖缺口处理清单-2026-10-27.md)。未知没有被转成失败；未测也没有被混进已运行未知。

| 缺口性质 | 当前处理 | 重新打开的条件 |
| --- | --- | --- |
| 原始返回、审批决定、云端实物不足 | 沿用已收尾记录；本轮不重复翻查、不让模型补写历史、不重跑来填旧分 | 自然取得可关联到同一次运行的新原始材料，再另存复核版本；没有新来源就保留未知 |
| 豆包早期正向归档与长结果后部未核完 | 历史正向5分、待核验6分分别保留，不包装成当前归档已支持 | 只有同次原始工具现场或可核验的旧导出才有帮助；后续成功不能倒填首次返回 |
| 任务授权范围不唯一 | ART04五款共同未知保留，停止靠更多读取旧成品解决题面歧义 | 先为新任务明确对象、期间和允许修改名单；新运行不回填旧任务 |
| 预设错误场景没有到达 | WorkBuddy基础回传两项保留“未有效测试” | 如日后另定补测，使用新目录、新记录；当前不要求重跑，也不认定回传丢失 |
| 压缩与权限共同条件未建立 | 分别登记为正式覆盖缺口，不折算满分或失败 | 先完成新测试的触发、允许／禁止、审批及证据设计，再决定可测试范围 |

可观测性中，WorkBuddy已经确认C步骤未在已审阅主执行链开始，也已经做过重开。O09「受阻结束原生状态」、O10「重开后历史完整」仍未知，是因为缺可关联的原生任务终态；不能再写“C状态未知”或“尚未重开”。元宝同样已有用户重开反馈，但缺原始返回、C状态及关联终态，复合要求仍不齐。两款沿用本轮停止追查决定，不重复要求重开。

来源保留未知，不意味着每项都值得继续投入时间。若旧现场已经无法补取，合理做法是保留它能证明的范围，在下一版题目中改进取证设计；不是把新跑结果移回旧记录。

## 6．问题原因目前能解释到哪一步

我们把“现象已确认”“执行环节有依据”“单因素对照验证原因”“修复后复测”分开描述。它们是报告中说明证据强弱的方法，不是额外评分。

下文的“代理”指产品在Python程序与实际文件操作之间增加的转交逻辑；EEXIST是“目标已经存在”的错误标记。目录创建参数允许目标已存在时，已有目录通常应当被接受；本例关注的正是产品这条执行路径为何仍报错。

| 案例 | 已观察事实与原因线索 | 尚不能写成什么 |
| --- | --- | --- |
| WorkBuddy基础回传保存回执失败 | 原版脚本在预设错误输出前提前退出20；第二轮不追加echo仍出现，说明echo不是该保存异常的必要条件 | 具体文件异常或内部责任已定位。更换目录、澄清提示词同时发生，不是只改一个因素的归因实验 |
| WorkBuddy旧正常任务目录异常 | 原生客户端独立诊断中，第一次创建目录成功，第二次允许已存在的创建操作在代理调用链报EEXIST，退出21；普通Python基线与受控源码检查提供辅助对照 | 原任务当时完整调用栈已取得、所有目录组合均有同一缺陷、底层原因已完全验证或缺陷已修复 |
| DSH三文件页脚版本未同步 | 可见修改范围判断排除了页脚，自检未覆盖页脚；112页仍旧，交付件与工作区对应 | 保存工具丢字、缓存交付旧文件，或某个Harness组件是唯一原因 |
| 判分解析程序两类问题 | 重复编号覆盖与package漏读在首批样例内有修正前后验证 | 这是产品自身缺陷，或七维完整评分程序已经验证可靠 |

WorkBuddy目录案例目前最适合作为后续原因验证候选，因为已有真实异常、原生客户端复现和明确调用位置。其诊断事实与边界（完整原件留本地；[公开维度摘要](../results/observability-review-2026-10-27-r1.md)）与既有结果解释（完整原件留本地；[公开维度摘要](../results/observability-review-2026-10-27-r1.md)）保留了限制。新版输入避免重复创建目录，是兼容处理；它改变了执行路径，不能当作代理缺陷修复。

候选验证应先固定诊断任务、实际模型、客户端及执行器版本、权限、输入指纹和判定规则，再只改变一个与目录创建有关的环节。可先以“调用时目标目录是否已存在”做最小条件对照：两个等价新现场使用同一脚本、相同创建参数，分别验证目录不存在与已存在时的返回、完整调用栈及文件状态。它只检验触发条件；若要进一步验证具体代理环节，需要能在真实客户端内单独替换或观察该环节，核对后端请求与返回，不能把普通Python绕开代理后的成功当成同环境修复。

对照前要保存预测：若“已有目录处理”是关键触发条件，不存在时应创建成功，已存在时应按允许已存在的语义正常返回；实际是否仍报EEXIST由新实验决定。每次使用新目录，记录额外动作与人工准备，不覆盖旧现场；若版本、模型、权限或输入同时变化，则该组结果不支持单因素结论。当前只提出设计，没有新运行、原因验证结果或修复结论。

## 7．结论适用范围

本阶段已经形成从题目、实际运行、逐项判断到七维结果与未知去向的材料链。它支持说明固定场景下观察到了什么、哪些差异是证据可获取程度造成的，以及若干异常的可见执行环节；还不支持普遍能力排名、稳定成功率、真实生产恢复能力或纯Harness组件的因果贡献。

限制主要有四点。第一，五款模型、自带技能、权限和执行环境没有统一，同一提示词也不等于实际操作完全相同。第二，多数场景每款只有一次当前运行，不能把偶然成功当成长期可靠。第三，原生日志保存的内容不一定等于完整实际模型请求；本地写入限制也不证明评测答案对产品完全不可读。第四，已有程序核对和首批合成样例验证，但尚无第二位独立人工评委对全部语义判断复核。

本轮检查只读核对了报告引用、状态覆盖、运行统计和来源保持情况，没有重新执行所有评分器或逐条重判全部原生轨迹。报告完成不等于实验缺口已补齐，文件指纹一致也不等于日志真实性或语义结论获得独立证明。
