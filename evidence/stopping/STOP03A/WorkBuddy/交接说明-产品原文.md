## 5. Named-target reasoning

The reported timestamp `2026-08-17T10:15:42Z` is **shared by two distinct commits**: the safe restore point `RP-880` at `0/C120000` and the destructive `TX-881` at `0/C130000`. A `recovery_target_time` stop at that instant cannot distinguish "stopped before the delete" from "stopped after the delete", so it is not an exact transaction boundary.

Therefore the plan uses the PostgreSQL recovery-setting spelling `target_type = "name"` with `recovery_target_name = before_batch_cleanup`, which resolves deterministically to LSN `0/C120000` — one commit before `TX-881` (`first_destructive_lsn = 0/C130000`). `recovery_target_action = pause` (the policy's `required_target_action`) keeps the candidate paused at the target rather than promoting or opening it to writes, which is exactly the state the invariant `database_accepts_writes = false` asserts.

**Rollback (drill side — no production impact):**
1. Keep the paused candidate untouched; do **not** run any promotion command. The candidate holds at `0/C120000` with `recovery_target_action = pause`.
2. Discard the isolated candidate by tearing down the restored data directory only; the archive (`archive/%f`) and all three backups remain untouched.
3. To re-drill, re-run the workflow from `verify-backup` — `state/recovery_state.json` can be reset to `phase = unready` and the steps repeated; the gate enforces the ordering.
4. If a probe ever fails or the two probes disagree, stop: do **not** call `close-gate`. The controller refuses the gate when `probe_runs != 2` or when `work/probe_report.json` does not match the expected two-pass document.
5. Re-verify the plan hash after any edit: `validate-plan` recomputes `plan_sha256`; `restore` refuses to run against a plan whose hash differs from the validated one.
