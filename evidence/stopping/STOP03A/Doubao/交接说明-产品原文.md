## 3. WAL 连续性

备份 `base-t2-0920` 结束于 `0/A300000`，目标还原点在 `0/C120000`。在 timeline 2 上，从 `0/A300000` 到 `0/C120000` 需要连续回放以下**全部可读** WAL 段：

| WAL 段文件名 | timeline | 起止 LSN | 可读 |
|---|---|---|---|
| `00000002000000000000000A` | 2 | `0/A000000` – `0/AFFFFFF` | 是 |
| `00000002000000000000000B` | 2 | `0/B000000` – `0/BFFFFFF` | 是 |
| `00000002000000000000000C` | 2 | `0/C000000` – `0/CFFFFFF`（含目标 `0/C120000`） | 是 |

段 `00000002000000000000000D`（`0/D000000` 起）起点已超过目标 LSN，**不需要**回放。WAL 段判定规则（end_lsn ≥ 备份 end_lsn 且 start_lsn ≤ 目标 LSN）与 `verify-backup` / `validate-plan` 返回的 `required_wal_segments` 完全一致（共 3 段）。

`restore_command_template` 采用策略指定的 `cp archive/%f %p`。

## 4. 命名恢复目标（named-target）推理

- `target_type = "name"`（对应 PostgreSQL 的 `recovery_target_name`）
- `target_name = "before_batch_cleanup"`（事件指定的 `last_known_safe_restore_point`，事件号 RP-880）
- `target_lsn = "0/C120000"`
- `recovery_target_action = "pause"`（策略 `required_target_action` 强制要求 pause，恢复到点后停住，不推进、不提升）

为什么不用时间戳：见第 2 节——RP-880 与 TX-881 共享 `2026-08-17T10:15:42Z`。命名还原点是一个**精确的、具名的事务边界**，它落在破坏性批次 TX-881（`0/C130000`，delete_active_customers_batch）之前，也落在 TX-882（`0/C140000`，write_cleanup_audit_marker）之前，从而保证：
