# CTX02「压缩后状态保持」：怎样确认压缩、怎样定位变化

这是一份尚未运行的检查方法。先确认测试条件，再看答案；不要从答错倒推“一定丢了历史”。

## 第一步：确认成功执行了什么

DSH原生手动压缩可能返回没有可压缩内容。保留按钮操作、提示和时间，再从原生日志中核对：

1. 出现本次`compaction/start`，表示开始尝试。
2. 出现对应`compaction/summary`，包含摘要及被替换消息范围／序号。
3. 摘要对应的新消息以替换操作进入有效会话；只记录摘要事件不代表它已经生效。
4. 出现对应`compaction/end`且没有错误；如有压缩编号或命令编号，用它们对应同一次操作。失败、缺结束或持久化错误不能算成功。

事件名称来自已检查的DSH代码，但本次运行仍须核对实际结构。上述检查不保证服务器处理了哪些输入。原生日志可保留旧消息用于审计；旧消息仍能在日志中查到，不代表它还在下一次有效模型请求里。

## 第二步：确认这16项要求真的经历了压缩

为每项指出初始值及最后更新所在消息，核对它们是否属于摘要替换的范围。不要只用事件序号大小粗略推断区间：存在历史替换时，实际消息顺序与编号大小可能不同，优先使用日志给出的实际被替换消息列表。

还要检查助手是否曾自行复述最终登记表、运行环境是否注入等价状态、是否存在可读取的外部记忆。如果最新值仍完整保留在未压缩消息中，答对只说明本次整体状态可用，不能归功于摘要保留。对相关项记“未隔离压缩影响”，保留产品行为，不人为删除这些消息。

若只覆盖部分检查点，逐项标记；没有覆盖的项不自动给0或1。日志缺失导致看不清范围时标“无法判断”。

## 第三步：把内容沿过程对应起来

| 材料 | 它能回答的问题 | 它不能单独证明什么 |
|---|---|---|
| 压缩前用户消息与有效上下文 | 原要求和更正是否已进入会话 | 模型最终实际收到什么 |
| 压缩摘要及替换记录 | 摘要写了什么，替换了哪些历史 | 某个字段没写进摘要就一定丢失；其他消息可能保留等价信息 |
| 压缩后的发送前基础正文 | 转换后的基础正文中还有没有有效信息 | 网络已投递、服务端已收到，或其他扩展没有作用 |
| 第六轮首次完整回复 | 产品最后用了什么值 | 单凭错值判断Harness故障 |

DSH取证插件可能记录到`purpose=compaction`的请求。若确实存在且能对应同一次压缩，可进一步检查摘要模型准备读取的内容。若缺少这份请求，不根据请求用途字段或普通日志推测它一定存在。

## 第四步：按证据决定责任说到哪里

| 实际发现 | 可以写 | 还需要排除什么 |
|---|---|---|
| 最终值错，过程证据不足 | 本次产品未保留正确状态，内部原因未知 | 原输入偏离、模型理解、Skill、压缩、格式解释等 |
| 摘要遗漏有效要求，但其他消息仍保留 | 摘要本身没有记录该要求 | 不能直接认定有效输入缺失或此次错误由遗漏造成 |
| 摘要模型的输入含要求，摘要及其后有效正文都没有等价信息 | 信息在本次压缩处理过程中未保留，具有直接线索 | 摘要模型选择与Harness压缩提示、范围、保留策略共同影响；不是纯Harness故障的充分证据 |
| 摘要含有效要求，后续基础正文却缺少，且没有等价保留 | 重点检查摘要进入会话及后续请求组装 | 是否为不同请求、观察副本是否完整、适配转换和其他扩展是否提供等价信息 |
| 后续正文含完整有效要求，最终仍给旧值 | 在已观察阶段没有发现传递缺失，继续分析回答应用阶段 | 模型理解、原生Skill、提示冲突；不能据此断言Harness所有机制正确 |

如需支持“压缩导致了本次退步”，再按相同输入、新会话、同一模型及设置做未压缩对照，保留全部运行。一次对照只增加线索，不宣称稳定因果；摘要模型也属于未完全排除的因素。

## 证据保存

按运行编号分别保存完整输入与回复、压缩前后日志、按钮操作及人工帮助、摘要替换范围、插件正文与文件指纹。逐项标明直接事实、原因线索和未知部分。额外录屏或改装插件提供的是评测证据，不给产品原生可观测性自动加分。
