# REC02「批量导出中断后续做」设计草案

版本0.1.0-design，2026-10-20。对应失败恢复维度的复杂部分12分。

**当前只完成题目设计，脚本和核对程序尚未实现，产品尚未运行，也未创建产品工作目录。** 下文命令是拟定接口，不是目前已经可以执行的程序。评分分配是本次设计建议，未改动REC01的规则或结果。

## 1. 要研究的具体问题

一个批量导出任务已经完成A批，B批写到一半失败，C批还没开始。继续执行时，产品能否保住A，妥善处理B的半成品，补完B和C，并验证最终结果没有缺失或重复？

REC01只检查“改一个参数后再执行”。本题增加的困难是：失败时已有文件和进度，重新从头跑、把半成品当完整结果，或者只补眼前报错却遗漏C，都可能导致错误。

这是人为设置的可复现故障，不是已发现的Harness缺陷。输出数据由程序处理，不要求模型写业务代码、计算复杂数据或调用办公Skill。

## 2. 任务与输入

用户需要把六项模拟活动的报名数据分三批导出，并生成一份总索引。

| 批次 | 原始数据 | 正确小计 |
|---|---|---:|
| A | ACT-51为18人，ACT-52为12人 | 30人 |
| B | ACT-53为9人，ACT-54为11人 | 20人 |
| C | ACT-55为15人，ACT-56为5人 | 20人 |

最终应有6项活动、70人，每项仅出现一次。固定数据作为[评测者标准](评测者材料/标准数据.json)保留；未来由原版脚本处理数据，模型不手工编写结果。

产品输入拟为一个仅依赖Python标准库的recovery_batch.py，数据内置，无需联网或安装依赖。每次操作只做一个步骤，不内置自动重试、自动清理或一键恢复策略。

最终交付拟为outputs下的batch_A.json、batch_B.json、batch_C.json和manifest.json。文件均包含本次任务编号run_id；这个编号在首次运行时生成，不同产品不要求编号相同，但同一次任务各文件必须一致。

## 3. 第一次运行会怎样失败

首次统一调用拟为：

```sh
python3 recovery_batch.py start
```

程序依次做以下事情：

1. 生成本次run_id，完成A批，保存完整文件及该批完成状态。
2. 开始B批，只写出ACT-53这一条，保存为batch_B.partial.json。
3. 返回预设的E_STREAM_INTERRUPTED错误，以非零退出码8结束；C批尚未执行。

B的半成品将是**语法合法、但内容不完整的JSON**，并明确标记complete=false。这样可以区分“文件能打开”和“业务结果完整”，不把语法正确误当恢复成功。

故障信息应明确说明A已完成、B有半成品、C未开始，并提供查看状态的方法。模拟故障只在首次B导出中发生一次；之后仍有半成品时，重新导出B会明确拒绝覆盖，要求先处理残留。不能让程序偷偷清理残留后自行恢复。

第一次失败后不能再次start来重建任务。后续恢复使用同一任务编号和已有状态。已有输出或目录权限等准备问题另记，不能混成预设故障8。

## 4. 产品可以用什么操作恢复

这些是拟定的基本工具操作，由同一个脚本提供，便于五款在不同系统环境下执行。它们不是Skill，也不是自动恢复组件。

| 拟定命令 | 只负责做什么 |
|---|---|
| status | 读取当前任务编号、各批状态、文件位置、完整/半成品标记 |
| discard-partial --batch B | 删除已标记的B批半成品，不触碰A和其他正式结果 |
| run-batch --batch B | 执行B这一批，成功后保存完整B结果；残留未处理时拒绝覆盖 |
| run-batch --batch C | 执行C这一批，不重新执行A或B |
| finalize | 在三批均完成且无活动半成品时生成总索引；不会自己补跑或清理 |
| verify | 只读检查完整性、重复项、任务编号、文件对应及人数合计，不修文件 |

完整调用形式均为python3 recovery_batch.py加上上述操作。允许不同的合理操作顺序，不因工具调用较多就自动扣分。每次修改任务状态的程序调用分别使用独立工具调用，保持操作与结果可以对应。

恢复策略仍由产品选择：先看哪里完成了、处理哪一个残留、补跑哪些批次、何时汇总和验证。若程序自己一键完成所有这些事，就不能用它评价产品的恢复调度。

## 5. 为什么分两轮运行

第一轮只执行start，遇到预设错误后停下。评测者保存A文件的指纹、B半成品、任务状态和原生执行记录。第二轮统一要求“在原任务中继续完成”，不给新的修复命令，让产品依据原始报错、已有状态和操作说明选择动作。

这样能对照恢复前后的文件，核实A是否被改动、半成品是否真正存在及被怎样处理。比只看最终文件更容易追溯问题。

这次停顿由评测者安排，必须记录人工介入。**本题不评价“报错后无人提醒也会立即自动恢复”，更不评价应用崩溃重启或跨会话恢复。** 两轮始终使用同一产品会话和任务目录，不手动压缩上下文。

本地产品由评测者只读复制现场；云端产品如能交付阶段文件，可独立检查。拿不到的阶段证据保持未知，不因最终正确而倒填初始状态。脚本自身的状态文件或事件记录只反映受测任务，不算产品原生执行日志，也不证明模型实际收到这些内容。

两轮拟用提示词分别为[首次运行与保存现场](提示词/01-首次运行后停止.md)和[继续完成原任务](提示词/02-继续完成原任务.md)。脚本未实现前不发送给产品。

## 6. 12分怎样分配

建议按四组分配：已完成进度3分、半成品处理4分、后续执行3分、验证2分。半成品稍高，因为合法但不完整的文件容易被误当完整结果，正是本题要观察的风险。

下表每个编号条件各1分，分别判定，不把一组强行全有或全无。

| 观察组 | 额度 | 每个1分条件 | 主要证据 |
|---|---:|---|---|
| 已完成进度保留 | 3 | ①恢复前后仍是同一run_id；②A文件前后字节指纹一致；③没有重新生成A批 | 失败现场、恢复后文件、对应原生操作；重新生成与否不能只看最终文件名 |
| 半成品正确处理 | 4 | ①有实际处理B残留的操作；②处理范围限于已标记B半成品，未删除其他正式结果；③重新生成的B含正确两项及20人；④最终总索引不把旧半成品当正式结果 | 前后文件对照、删除/隔离操作、B完整结果及总索引 |
| 后续执行完成 | 3 | ①同会话同目录中的恢复操作实际运行；②此前未开始的C批完成且数据正确；③总索引恰好关联同任务的A、B、C，6项活动无遗漏重复，合计70人 | 原生操作与结果、C文件、三个批次与总索引的独立核对 |
| 恢复结果经过验证 | 2 | ①实际执行过覆盖数据完整性、重复、任务编号和半成品排除的验证；②该验证回报通过，且与评测者独立检查一致 | 验证调用及其结果、独立核对报告；不能只凭“已验证”的文字 |

①②③等是每组内部的条件编号，不是新的维度。12项均应分别记录判断、证据位置、复核方法、置信依据和限制。

条件有明确反例才判0；缺少证据写无法判断；对应执行阶段没有触发则留空。没有发起恢复调用，不能据此认定Harness底层不能执行；没有验证调用，也不能推断底层不支持验证。产品是否主动继续、主动验证另记行为，不拿未知的内部原因直接扣成Harness故障。

未发生预设故障、手工改结果、修改脚本或重建任务，会影响相应项目的有效性。保存偏离现场，不让产品反复重来直到通过。最终文件是否完整不能替代对恢复过程的判定。

## 7. 怎样归因，避免把脚本能力算给Harness

- 程序提供批次状态和文件操作。**不把程序写出的检查点称为Harness原生检查点能力。** 本题测的是产品能否围绕已有任务状态继续安排、执行和核对操作。
- 固定数据、预设故障、清晰操作说明减少业务推理和Skill差异；选择恢复顺序、清理范围与验证时机仍有模型参与。12分是原生配置下的恢复场景表现，不能直接当纯Harness因果分。
- 若正确操作根本没有发起，先记录行为，原因可能涉及模型、Skill或系统指令；若正确操作已发起但没有实际执行，才沿执行链路继续排查。
- 若A被改动，先查具体写/删操作是谁发起的。模型明确请求删错文件，与工具执行了模型没要求的删除，是不同原因，不能只看损坏结果就统一归责Harness。
- 若最终正确但没有原生返回，只能确认可独立验证的文件事实；不能补写模型收到的内容。五款的证据层、置信依据和未知项分别报告。

## 8. 实现前后应做的工作

本稿先把场景、两轮协议和12分观察项说明白。后续若采用，再实现单步骤脚本和独立核对程序，自检故障是否确定发生、是否真的留下半成品、已有成果是否可对照、是否会重复或误覆盖；随后只在DSH先行试测。

自检不算产品成绩，模拟故障不算产品真实缺陷。正式跨产品比较前固定同版脚本、提示词和判分标准。其他四款仅调整本地目录或云端附件入口，不改变恢复目标。
