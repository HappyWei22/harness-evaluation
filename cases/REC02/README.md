# REC02「批量导出中断后续做」

版本1.0.0，自制复杂题，占失败恢复维度12分。五款本轮均已结束，输入、两轮核心提示词及评分规则使用同版材料。

## 为什么需要两轮

脚本第一次 `start` 故意退出8：A完整，B留下有效但不完整的JSON，C未开始。第一轮只观察并停下，评测者先保存失败现场，再由用户在原会话发送继续提示词。否则最后只有一套正确文件，难以判断此前A是否保住、B半成品怎样处理。

第二轮提供status、只丢弃B半成品、补跑指定批次、finalize和verify等操作接口，产品安排执行顺序。目标是保住A、处理B、完成B/C和总索引，共6个活动、70人。状态与事件由题目脚本生成，不是产品原生检查点或事务恢复机制。

## 材料与操作

- [原版输入脚本](输入/recovery_batch.py)：只复制这一文件到产品的新空目录，不复用旧任务。
- [第一轮：执行后停止](提示词/01-首次运行后停止.md)、[第二轮：继续原任务](提示词/02-继续完成原任务.md)。先保存失败现场再发送第二轮。
- [规则](用例与判分规则.md)、[12项观察表](评测者材料/12项观察表.json)、[固定标准数据](评测者材料/标准数据.json)。
- [独立文件检查](checks/核对阶段文件.py)：只读检查阶段文件，不执行输入脚本，不自动给12分。
- [早期设计稿](设计草案.md)保留历史，不代表当前仍未实现或应该按旧稿运行。

元宝不能选本地目录，先把附件原样复制到新的云端目录；两轮核心任务条件不变。云端快照收集是额外人工取证，不能算自主恢复步骤。本轮快照收集方法与证据边界见[来源说明](../../docs/公开材料与来源说明.md)。

## 本轮结果

Codex、DSH、WorkBuddy、豆包工作分别确认12项通过；元宝确认7项，另5项因缺原生工具结果正文保持未知，不记0，不按已评比例换算满分。五款最终文件均正确，不能依据未知项给元宝排末位。

见[失败恢复结果及证据索引](../../results/failure-recovery.md)。脚本verify的10项、独立文件检查的13项与评分12项分别计数。人工暂停与继续不等于无人提醒的自动恢复，也没有测试应用崩溃、重启或跨会话恢复。
