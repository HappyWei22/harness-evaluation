# Harness 能力评测与失败分析

**第一阶段记录 · 截至2026年10月17日。**

Agent没有完成任务，可能是模型理解了错误要求，也可能是工具没有执行、报错没完整返回，或生成的文件没有保存到正确位置。本项目希望先检查实际发生了什么，再根据执行记录分析原因。

Harness是负责组织模型调用、工具执行、结果回传和任务状态的系统层。产品自带的Skill（操作指南或脚本）、模型和运行环境也会影响结果，所以这里先比较有证据支持的执行行为，再讨论能否定位到具体原因。

测试对象是Codex、WorkBuddy、DeepSeek Harness（DSH）、元宝专家模式和豆包办公。当前已经确定七个维度，并开展信息回传三道测试、上下文管理一道基础测试。其余维度尚未完成共同测试，目前没有完整100分成绩或五款总排名。

## 为什么这样设计

前期主要通过公开办公题试跑寻找问题。实践中发现，复杂任务失败往往混合业务理解、文件处理和工具执行等因素，难以直接对应具体能力。随后调整为先明确评测标准、观察项和判定依据，再构造能够触发对应行为的专项任务。

例如，要检查长输出的处理，就让固定程序生成报告，分别观察截断说明、全文入口、后续读取和文件保存。完整思考过程见[探索过程与方法调整](docs/探索过程与方法调整.md)。

## 当前结果怎样理解

信息回传包含五款产品、三道题，每题四项，共60项判断。**这表示60个检查条目，不是60次独立运行。** 其中部分仍因缺证据、尚未核完或测试条件不成立而留空。

| 产品 | 历史确认分值 | 当前有归档支持的正向分值 | 还需要说明的部分 |
|---|---:|---:|---|
| Codex | 14 | 14 | 4分明确未通过，2分未知 |
| WorkBuddy | 16 | 16 | 2分明确未通过，2分未有效测试 |
| DSH | 19 | 19 | 1分未知 |
| 元宝专家模式 | 暂无 | 暂无 | 20分无法判断 |
| 豆包办公 | 9 | 4 | 历史正向5分待补现场，另5分未知、6分待补核验 |

每款总额度是20分，但上述数字不能直接写成完整“得分/20”或排名。历史分值与当前证据状态分列，是为了保留原记录并说明哪些判断现在可以复核，详见[逐项结果](results/information-feedback.md)。

上下文基础题中，五款本轮均保留未改的编号、币种，并采用更新后的地点和预算，各为4/4。这只覆盖三轮短对话，复杂16分及长上下文压缩尚未测试。

取证工具基于社区dsh-context 0.72.0增加了所选上下文JSON导出和原生日志ZIP下载。前者保存插件根据日志还原的内容，后者复用DSH已有下载功能；它们不能证明实际模型请求已被截获。来源、增量改动和验证范围见[插件扩展](tools/dsh-context-export/README.md)。

## 怎样检查这些评分有没有材料依据

结果表给出了分数，还需要能找到与分数对应的实际记录。因此，仓库附有`checks/verify.py`，用于读取已有材料，按写好的检查条件核对记录是否一致。主要检查：

- **文件是否与记录一致：** 比较文件大小和SHA-256文件指纹，检查测试程序或证据文件是否发生变化。
- **现场是否支持相应判断：** 对已有充分归档的项目，把工具实际返回与本次预期结果比较，检查状态、指定字段和完整文件字节。
- **评分记录是否对应：** 检查汇总分值与单项记录是否一致，并保留缺证据、尚未核完和未有效测试的状态。

这个程序只读取仓库里的文件，不会重新打开五款产品、调用模型或执行测试输入程序。

使用Python 3.9或更新版本，进入包含本README的仓库根目录后运行：

```bash
python3 checks/verify.py
```

这条命令核对60项信息回传记录和五款上下文基础题。对于证据不足的条目，只检查记录来源和留空状态，不会自动给产品判通过。

如果只想检查WorkBuddy在FB03「截断后完整结果获取」中的第四项“全文保存准确性”，运行：

```bash
python3 checks/verify.py --item WB-FB03-04
```

`--item`表示选择观察项；`WB`代表WorkBuddy，`FB03`代表上述测试，`04`代表第四项。程序会核对该项记录和对应现场，同时仍检查仓库全部文件的指纹。

**核对程序运行成功，与产品这一项得分是两回事。** 例如，WorkBuddy保存的文件比预期多2058个回车字符。程序确认这个差异与记录一致，就完成了核对；但按“保存文件必须逐字节一致”的规则，产品这一项仍为0分。

运行后会输出JSON格式的核对结果。终端结束状态为0，表示本次材料符合程序列出的检查条件；结束状态为1，会给出具体不符原因。这些检查还不能证明模型实际收到的全部信息或产品内部根因。各输出字段、检查范围与限制见[复核说明](docs/复核说明.md)，实际执行记录见[材料核对记录](checks/整理检查结果.md)。

## 开展新的测试

每次使用独立空目录和新会话，只给产品指定输入及提示词。仓库中包含预期结果和历史证据，不应直接作为受测产品的工作区。保留规则版本，记录实际模型、产品版本、权限、环境、命令及人工介入；无法取得的信息写未知，新结果另建记录。

## 材料范围

仓库提供与判分有关的工具事件、可见问答和必要文件。原始行号保留在source_line中，本机路径及分享入口已替换；完整原生日志不在这里，因此不能据摘录推断未公开部分的内容。

模拟报告程序保持原始字节。文件来源及处理方式见[材料与来源说明](docs/公开材料与来源说明.md)和[PROVENANCE.json](PROVENANCE.json)，文件指纹清单为[MANIFEST.json](MANIFEST.json)。第三方公开题原附件、答案库、完整本机运行数据及受测产品本体源码未收入；工具目录中的社区插件派生源码保留原作者信息和Apache-2.0许可证。下一步见[待完成事项](docs/待完成事项.md)。
