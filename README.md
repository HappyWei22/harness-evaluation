# Harness 能力评测与失败分析

**阶段记录 · 截至2026年10月30日，已完成七维比较资格审阅、114条历史记录的审阅覆盖与十项统一整理，并补充WorkBuddy局部原因验证的交付和再次复核；没有完整100分成绩或五款排名。**

Agent没有完成任务，可能是模型理解了错误要求，也可能是工具没有执行、报错没完整返回，或生成的文件没有保存到正确位置。本项目希望先检查实际发生了什么，再根据执行记录分析原因。

Harness是负责组织模型调用、工具执行、结果回传和任务状态的系统层。产品自带的Skill（操作指南或脚本）、模型和运行环境也会影响结果，所以这里先比较有证据支持的执行行为，再讨论能否定位到具体原因。

测试对象是Codex、WorkBuddy、DeepSeek Harness（DSH）、元宝专家模式和豆包办公。当前已经确定七个维度，已有信息回传三道题、上下文管理基础题与压缩探索题、失败恢复两道题，以及权限基础题和授权/间接访问适配验证。产物保存与交付完成五款各四题先行试测，并限时复核待定项；停止条件完成五款各四场景的本轮执行与归档，未知项单列。可观测性完成五款各三题的新版执行、归档与重开检查，同标准复核后38项确认、12项未知；权限仍缺五款共同条件下的正式比较。目前没有完整100分成绩或五款总排名。

各结果表保留其日期下的原判断；哪些观察可以进入正式比较，以[10月30日逐项审阅](docs/阶段进展/七维审阅汇报-2026-10-30.md)及其限制为准。114条是历史记录，包含诊断和无效尝试，不等于114次有效业务运行。

## 为什么这样设计

前期主要通过公开办公题试跑寻找问题。实践中发现，复杂任务失败往往混合业务理解、文件处理和工具执行等因素，难以直接对应具体能力。随后调整为先明确评测标准、观察项和判定依据，再构造能够触发对应行为的专项任务。

例如，要检查长输出的处理，就让固定程序生成报告，分别观察截断说明、全文入口、后续读取和文件保存。完整思考过程见[探索过程与方法调整](docs/探索过程与方法调整.md)。

## 当前结果怎样理解

统一台账截至10月27日登记114次任务，其中93次供当前评分引用；都不是成功数。10月28日目录诊断的4次实际探针、1次加载辅助及1个未执行排队会话另列，不回写历史总数。各维度单位和条件不同，详见总表及最新阶段进展。

10月21日新增的PERM01、PERM02及WorkBuddy规则补充实验，全部属于“权限边界”这一维度。它们分别检查普通受限写入、A请求获准后的后续B调用、链接与子进程访问，以及文件规则更新后的执行。具体让产品做什么、为什么设置正常对照、哪些段落尚未运行，见[当天任务设计与进展](docs/阶段进展/2026-10-21.md)。题目数量和调用数量不等于已完成的维度数量。

信息回传包含五款产品、三道题，每题四项，共60项判断。**这表示60个检查条目，不是60次独立运行。** 其中部分仍因缺证据、尚未核完或测试条件不成立而留空。

## 怎样检查这些评分有没有材料依据

结果表给出了分数，还需要能找到与分数对应的实际记录。因此，仓库附有`checks/verify.py`，用于读取已有材料，按写好的检查条件核对记录是否一致。主要检查：

- **文件是否与记录一致：** 比较文件大小和SHA-256文件指纹，检查测试程序或证据文件是否发生变化。
- **现场是否支持相应判断：** 对已有充分归档的项目，把工具实际返回与本次预期结果比较，检查状态、指定字段和完整文件字节。
- **评分记录是否对应：** 检查汇总分值与单项记录是否一致，并保留缺证据、尚未核完和未有效测试的状态。

这个程序只读取仓库里的文件，不会重新打开五款产品、调用模型或执行测试输入程序。

使用Python 3.9或更新版本，进入包含本README的仓库根目录后运行：

```bash
python3 checks/verify.py
```

这条命令核对60项信息回传记录、五款上下文基础题、75项失败恢复记录、五款CTX02探索材料，以及权限运行台账、必要原生事件和实际文件。新增产物交付检查还核对20次运行、50个有效观察项的评分来源、累计、8项待定及日志结构/取回字节差异；不重跑缺少原附件的Office任务。停止条件检查另外核对20份记录、50项观察、恢复JSON摘要、受阻终态及元宝留空状态；可单独运行 `python3 checks/verify_stopping.py`。对于证据不足的条目，只检查记录来源和留空状态，不会自动给产品判通过。新增 `python3 checks/calibrate_observability.py` 运行首批9个合成校准样例；总入口将其与产品运行分开核对，原评分不自动重算。新增 `python3 -B checks/verify_observability_review.py` 核对同标准复核版本与四项改判，旧版检查继续保留。可观测性历史版检查还核对15次新版任务、50项来源分值、181条必要原生摘录中的业务配对、内部退出码与错误、产物内容、重开来源及未知状态；可单独运行 `python3 checks/verify_observability.py`。权限材料也可单独用 `python3 checks/verify_permissions.py` 核对，含5种人为改坏材料的拒绝检查；这不是新增产品运行或独立判卷准确率。

如果只想检查WorkBuddy在FB03「截断后完整结果获取」中的第四项“全文保存准确性”，运行：

```bash
python3 checks/verify.py --item WB-FB03-04
```

`--item`表示选择观察项；`WB`代表WorkBuddy，`FB03`代表上述测试，`04`代表第四项。程序会核对该项记录和对应现场，同时仍检查仓库全部文件的指纹。

**核对程序运行成功，与产品这一项得分是两回事。** 例如，WorkBuddy保存的文件比预期多2058个回车字符。程序确认这个差异与记录一致，就完成了核对；但按“保存文件必须逐字节一致”的规则，产品这一项仍为0分。

运行后会输出JSON格式的核对结果。终端结束状态为0，表示本次材料符合程序列出的检查条件；结束状态为1，会给出具体不符原因。这些检查还不能证明模型实际收到的全部信息或产品内部根因。各输出字段、检查范围与限制见[复核说明](docs/复核说明.md)，实际执行记录见[材料核对记录](checks/整理检查结果.md)。

## 开展新的测试
